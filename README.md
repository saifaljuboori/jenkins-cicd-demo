# Branch 5 — GitHub Webhook

## Goal

Configure GitHub and Jenkins so that a push to the application repository automatically triggers the Jenkins CI/CD pipeline.

This branch completes the project by introducing:

* GitHub Webhooks
* Automatic Jenkins pipeline triggering
* Jenkins-to-GitHub version commits
* Commit-loop prevention
* SCM Skip Plugin
* End-to-end GitHub → Jenkins → Docker Hub flow

Branch 4 established automated application versioning and the ability for Jenkins to commit the updated `pom.xml` back to GitHub.

Branch 5 adds the missing event-driven trigger mechanism and ensures that the commit generated by Jenkins does **not** trigger the pipeline again.

---

## 1. Final CI/CD Flow

The final pipeline works as follows:

```text
Developer
    │
    │ git push
    ▼
GitHub Repository
    │
    │ Push Webhook
    ▼
Jenkins
    │
    ├── SCM Skip Check
    │
    ├── Increment application version
    │
    ├── Build JAR
    │
    ├── Build Docker image
    │
    ├── Push Docker image
    │
    ├── Deploy
    │
    └── Commit updated pom.xml
            │
            │ git push
            ▼
       GitHub Repository
            │
            │ Push Webhook
            ▼
         Jenkins
            │
            └── SCM Skip detects [skip ci]
                    │
                    └── Pipeline is skipped
```

The important part is the final loop:

```text
Jenkins
   ↓
GitHub
   ↓
pom.xml version update
   ↓
GitHub webhook
   ↓
Jenkins
```

The second Jenkins execution must be prevented.

---

# 2. Configure the Jenkins GitHub Trigger

Open the Jenkins pipeline job.

Go to:

```text
Jenkins
→ Pipeline Job
→ Configure
→ Build Triggers
```

Enable:

```text
GitHub hook trigger for GITScm polling
```

This allows a GitHub webhook to notify Jenkins when a push occurs.

The Jenkins GitHub plugin uses the webhook to trigger its internal Git SCM polling logic.

---

# 3. Configure the GitHub Webhook

Open the application repository on GitHub.

Go to:

```text
Repository
→ Settings
→ Webhooks
→ Add webhook
```

Configure the webhook as follows.

### Payload URL

```text
http://159.65.112.17:8080/github-webhook/
```

> This URL is specific to the DigitalOcean Jenkins server used in this lab.

### Content type

```text
application/json
```

### Events

Select:

```text
Just the push event
```

Leave the other events disabled.

GitHub sends the webhook when the subscribed repository event occurs. The `push` event represents a push to a repository branch.

---

# 4. How the Webhook Works

The normal application-development flow is now:

```text
Developer changes application
        │
        ▼
git push
        │
        ▼
GitHub
        │
        │ HTTP POST
        ▼
Jenkins /github-webhook/
        │
        ▼
Jenkins detects SCM change
        │
        ▼
Pipeline starts
```

This removes the need for a developer to manually start Jenkins after every GitHub push.

GitHub Webhooks are designed specifically to notify external systems when repository events occur, including triggering CI systems after a push.

---

# 5. Why the Commit Loop Happens

Branch 4 introduced the `commitVersion()` functionality.

At the end of the pipeline, Jenkins changes the Maven version:

```text
1.4.16
   ↓
1.4.17
```

The updated `pom.xml` is then committed and pushed back to GitHub:

```text
Jenkins
   ↓
git add pom.xml
   ↓
git commit
   ↓
git push
   ↓
GitHub
```

Because GitHub sees a new push, the webhook sends another notification to Jenkins:

```text
GitHub
   ↓
Webhook
   ↓
Jenkins
```

Without protection, Jenkins would execute the pipeline again.

The second execution would increment the version again:

```text
1.4.17
   ↓
1.4.18
```

Then Jenkins would push another commit:

```text
1.4.18
```

which would trigger Jenkins again.

The result would be an endless CI loop.

---

# 6. Mark Jenkins-Generated Version Commits

The `commitVersion()` function from Branch 4 creates the commit using:

```bash
git commit -m "chore: increment application version [skip ci]"
```

The important part is:

```text
[skip ci]
```

The commit message therefore identifies the commit as one that should not start another CI build.

For example:

```text
chore: increment application version [skip ci]
```

However, simply putting `[skip ci]` into the commit message does **not automatically stop Jenkins**.

Jenkins needs a mechanism that actually evaluates the commit message and skips the pipeline.

---

# 7. SCM Skip Plugin

The SCM Skip Plugin was installed on Jenkins to solve this problem.

The plugin can inspect SCM commit messages and skip a Pipeline when the commit message matches a configured regular expression. For Pipeline jobs, the plugin is used as the `scmSkip` Pipeline step.

The plugin documentation recommends placing the `scmSkip` step early in the Pipeline so that no unnecessary stages execute before the skip decision is made.

---

# 8. Add the SCM Skip Check

The Jenkinsfile was updated with an initial stage:

```groovy
stage("SCM Skip Check") {
    steps {
        scmSkip(
            deleteBuild: true,
            skipPattern: '.*\\[skip ci\\].*'
        )
    }
}
```

The complete beginning of the pipeline therefore looks like:

```groovy
stages {
    stage("SCM Skip Check") {
        steps {
            scmSkip(
                deleteBuild: true,
                skipPattern: '.*\\[skip ci\\].*'
            )
        }
    }

    stage("increment version") {
        steps {
            script {
                incrementVersion()
            }
        }
    }
```

The regular expression:

```text
.*\[skip ci\].*
```

matches any commit message containing:

```text
[skip ci]
```

Therefore this commit:

```text
chore: increment application version [skip ci]
```

matches the pattern.

The SCM Skip Plugin then aborts the Pipeline before the remaining stages execute.

---

# 9. Why the `scmSkip` Stage Must Be Early

The skip check is intentionally the first Pipeline stage:

```text
SCM Skip Check
      ↓
increment version
      ↓
build JAR
      ↓
Docker image
      ↓
Docker push
      ↓
deploy
      ↓
commit version
```

If the incoming commit is a normal application change:

```text
feat: add new endpoint
```

it does not match:

```text
.*\[skip ci\].*
```

and the Pipeline continues normally.

If the incoming commit is Jenkins' version commit:

```text
chore: increment application version [skip ci]
```

the first stage detects the pattern and stops the Pipeline.

---

# 10. Final Jenkinsfile Structure

The final Branch 5 pipeline follows this structure:

```groovy
@Library('jenkins-shared-library') _

pipeline {
    agent any

    tools {
        maven 'my-maven'
    }

    stages {

        stage("SCM Skip Check") {
            steps {
                scmSkip(
                    deleteBuild: true,
                    skipPattern: '.*\\[skip ci\\].*'
                )
            }
        }

        stage("increment version") {
            steps {
                script {
                    incrementVersion()
                }
            }
        }

        stage("build jar") {
            steps {
                script {
                    buildJar()
                }
            }
        }

        stage("build and push docker image") {
            steps {
                script {
                    def version = getVersion()

                    env.IMAGE_NAME = "saljuboori/demo-app:${version}"

                    echo "Docker image: ${env.IMAGE_NAME}"

                    buildDockerImage(env.IMAGE_NAME)
                    dockerLogin()
                    dockerPush(env.IMAGE_NAME)
                }
            }
        }

        stage("deploy") {
            steps {
                script {
                    echo "deploying the application..."
                }
            }
        }

        stage("commit version") {
            steps {
                script {
                    commitVersion()
                }
            }
        }
    }
}
```

# 11. End-to-End Example

Assume the application currently contains:

```xml
<version>1.4.16</version>
```

A developer makes an application change:

```text
feat: add new application functionality
```

and pushes it:

```bash
git add .
git commit -m "feat: add new application functionality"
git push
```

### Step 1 — GitHub

GitHub receives the push.

```text
Developer
    ↓
GitHub
```

GitHub sends the configured push webhook:

```text
http://159.65.112.17:8080/github-webhook/
```

### Step 2 — Jenkins

Jenkins receives the webhook and starts the pipeline.

The SCM Skip stage checks:

```text
feat: add new application functionality
```

There is no:

```text
[skip ci]
```

so the pipeline continues.

### Step 3 — Increment Version

Jenkins changes:

```text
1.4.16
```

to:

```text
1.4.17
```

### Step 4 — Build

Jenkins builds:

```text
java-maven-app-1.4.17.jar
```

### Step 5 — Docker

The Docker image is tagged:

```text
saljuboori/demo-app:1.4.17
```

and pushed to Docker Hub.

### Step 6 — Deploy

The deployment stage executes.

### Step 7 — Commit Version

Jenkins commits:

```text
chore: increment application version [skip ci]
```

and pushes it to GitHub.

### Step 8 — GitHub Webhook Fires Again

GitHub sees the Jenkins-generated push and sends another webhook.

```text
GitHub
   ↓
Webhook
   ↓
Jenkins
```

### Step 9 — SCM Skip Stops the Loop

Jenkins checks:

```text
chore: increment application version [skip ci]
```

The commit matches:

```text
.*\[skip ci\].*
```

Therefore the Pipeline is skipped.

No second version increment occurs.

No second Docker image is built.

No second Docker push occurs.

No second deployment occurs.

The CI loop is stopped.

# 12. What Was Tested

The SCM Skip configuration was manually tested against the actual Jenkins pipeline.

The Pipeline used:

```groovy
scmSkip(
    deleteBuild: true,
    skipPattern: '.*\\[skip ci\\].*'
)
```

The Jenkins-generated commit was:

```text
chore: increment application version [skip ci]
```

The resulting Git history showed the Jenkins version commits followed by the SCM Skip configuration commit.

The important result was:

```text
SCM Skip prevented the commit loop build.
```

This confirms that the commit-loop prevention mechanism works in this project rather than merely being theoretical configuration.

# 13. Important Distinction: Branch 4 vs Branch 5

Branch 4 and Branch 5 have different responsibilities.

### Branch 4

Branch 4 introduced:

```text
Automatic application versioning
        ↓
Read Maven version
        ↓
Version Docker image
        ↓
Commit updated pom.xml
```

The `commitVersion()` function can technically operate without a GitHub webhook.

It simply performs:

```text
Jenkins
   ↓
modify pom.xml
   ↓
git commit
   ↓
git push
   ↓
GitHub
```

### Branch 5

Branch 5 introduces:

```text
GitHub
   ↓
Webhook
   ↓
Jenkins
```

and solves the interaction between:

```text
GitHub webhook triggering
```

and:

```text
Jenkins committing back to GitHub
```

by adding:

```text
SCM Skip
```

Therefore Branch 5 completes the event-driven CI/CD workflow.

# 17. Result

The completed demonstration now provides an event-driven CI/CD workflow:

```text
Application Change
       ↓
     GitHub
       ↓
   Webhook
       ↓
    Jenkins
       ↓
 Version Application
       ↓
    Build JAR
       ↓
 Build Docker Image
       ↓
 Push Docker Image
       ↓
     Deploy
       ↓
 Commit Version
       ↓
     GitHub
       ↓
   Webhook Again
       ↓
 SCM Skip Detection
       ↓
     SKIPPED
```

The key lesson is that **Jenkins can both consume changes from GitHub and write version changes back to GitHub without creating an infinite CI loop**, provided that Jenkins-generated commits are explicitly identifiable and excluded from subsequent Pipeline execution.
